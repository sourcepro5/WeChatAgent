# WeChat 4.1.15.13 x64: native text, image and mention APIs

This adds an **exact-version native sender**, not a blanket version allowlist.
The existing 4.1.10.27 proxy-DLL path and pinned upstream-source build are unchanged.
For 4.1.15.13 the project loads its own text DLL into an already-running matching
WeChat process. It does not replace client files, downgrade WeChat, activate a
window, simulate input or modify recall behavior.

The `media-mentions-v2` revision extends the text-only contribution in PR #3.
It exposes native image and group-mention HTTP APIs. **This contribution does
not wire image/at segments into HookOneBot or add new model tools/UI.** The
existing OneBot text route remains unchanged. Callers of the new APIs must
resolve real conversation/member IDs and confirm receipts before reporting
delivery; the capability flag alone does not implement that higher layer.

## Scope and checks

- Private and group **text** use the existing `/SendTextMsg` request shape.
- Health retains `integration: WeChatAgent-1`, loopback Bearer authentication,
  live database-account metadata and the existing account/version checks.
- The loaded core must match 4.1.15.13, `SizeOfImage = 202039296`, send-entry bytes
  and the sender vtable. A construction-only probe verifies the final text
  message type, empty native strings and callback layout before readiness.
- The text field is `message + 0x758`, not the nearby base-message string field.
  Allocation, callback ownership and destruction use this profile's layout.
- Submission is serialized. Native exceptions fault the component; the adapter
  keeps its existing uncertain-delivery handling and does not blindly resubmit.
- A native `ret: 0` means **accepted only**. The unchanged NT-reader/OneBot adapter
  still requires a new own-message row, matching target/text and a nonzero server
  ID. It is not a read receipt.
- `nativeImageSend` and `nativeMentionSend` are true only after startup has
  constructed/destroyed all three mapped message objects without sending.
  `nativeStickerSend` and `nativeQuoteSend` remain **false**. No image or sticker
  offsets from 4.1.10.27 are reused.

## Build and select

Prepare the existing header dependencies under `components/WeChat-Hook` as
described in [WECHAT_HOOK.md](WECHAT_HOOK.md), plus VS 2022 C++ Build Tools (v143).
Only `httplib.h` and `json.hpp` are included by this new standalone build; no old
send implementation is linked. Alternatively pass a source directory containing
`include/json.hpp` and `3rdparty/httplib/httplib.h` via `-HeadersRoot`.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-hook.ps1 -TargetVersion 4.1.15.13
```

For a manually configured compiler environment, invoke `build-hook-current.ps1`
with `-VcVars` pointing to its VS 2022 `vcvars64.bat`.
Build products stay under ignored `state/hook/native-4.1.15.13/` and are not
included in the source contribution. No compile step operates WeChat.

In your local `config/wechatagent.json`, set:

```json
{
  "hook": {
    "expectedVersion": "4.1.15.13",
    "wechatExecutable": "client/Weixin.exe"
  }
}
```

The block illustrates two fields to change in the existing full configuration,
not a replacement configuration. Set `wechatExecutable` to your actual signed
4.1.15.13 executable; keep the existing loopback URL, timeouts and account setup.
Run project configuration preparation as usual, open exactly one matching
WeChat main process yourself, then run `npm run hook:open` and `npm run hook:check`.
The loader verifies the built DLL/loader hashes and process path before loading;
the DLL independently verifies the loaded core. It will not restart WeChat.
Configuration/token files are generated beside the DLL from the project's
existing private token. They are not copied into the WeChat installation.

This profile does not pin or disable updates in the system WeChat installation.
After an update, a new matching profile must be reviewed; changing a version
string is not sufficient. After upgrading from text-v1 or rebuilding, exit/reopen WeChat
normally before loading the new build; no forced unload/reload is attempted.
The loader requires the new revision's live health and rejects a still-loaded
old DLL rather than claiming the new APIs are ready. Historical DLL/loader
filenames are retained for existing build/launch paths.

## Native API additions (not OneBot segments)

Both routes require the existing `Authorization: Bearer <local token>` and
`X-WeChatAgent-Account: <verified account directory>` headers. They share the
same loopback listener, account gate and serialization mutex as text.

### POST /SendImgMsg

```json
{"wxidorgid":"<real conversation ID>","path":"<absolute local outgoing-image path>"}
```

`load-hook-current.ps1` creates `state/hook/outgoing-images` and writes its
absolute location into the private DLL config as `imageRoot`. Place outgoing
PNG/JPEG/WebP files there. Canonical paths escaping that root, directories,
empty files, files over 32 MiB, URLs and unsupported signatures are rejected
before native submission. No download or arbitrary file send is performed.
The image object uses its own constructor/vtables, a native wide path at
`+0x120`, basename at `+0x1a8`, type 3 and actual source byte count.

### POST /SendTextAtMsg

```json
{"wxidorgid":"<real group ID>@chatroom","msg":"<display text>","atUserIds":["wxid_example"]}
```

Only group targets and 1-8 explicit member IDs are accepted; duplicate IDs are
removed. IDs must use letters, digits, `_` or `-`; display names, separators
and `notify@all` are rejected. The caller is responsible for mapping and
checking these IDs against the intended group's trusted member data. Display
text is not an identity lookup. Real notification metadata is written into
the constructor-owned native `at_user_list` string at `+0x778`, separately
from `text_content` at `+0x758`.

### Result semantics

`{"ret":0,"retmsg":"accepted"}` means submission only, **not delivery**.
Invalid input is HTTP 400; unavailable/mismatched account is HTTP 409; a native
submission fault is HTTP 503 and faults the backend. Do not automatically
retry an uncertain submission or fall back to UI input.

The host should snapshot the target's outgoing rows before submit and require
a new own-message row with a nonzero server ID afterwards. Image confirmation
must identify the intended image, not just any new type-3 row. Mention
confirmation must additionally match the exact `source/atuserlist`, not merely
the displayed `@name`. The generic text receipt matcher does **not** provide
these checks; it is not reused to pretend the new API delivery was verified.

## Evidence and portable validation

The underlying 4.1.15.13 x64 mapping was exercised on 2026-10-21: one self-chat
text submission while the client was minimized, a new server message ID after
about 1.63 seconds, no foreground focus change, and subsequent authorized text
replies through the same implementation. This source contribution removes the
local application's paths/names and adopts WeChatAgent's contracts. **That live
test is evidence for the original mapping, not a claim that this port was run
against another user's client.** No personal account, token, messages, binaries
or raw database records are included.

```powershell
node --test scripts/test-hook-41513.mjs scripts/test-hook-native-apis-41513.mjs scripts/test-hook-startup.mjs scripts/test-wechat-account-check.mjs scripts/test-hook-launcher.mjs
```

These tests are isolated fixtures. They verify exact-version/account rejection,
current-profile readiness, old-profile compatibility, token/target contracts,
server-receipt confirmation and no replay after uncertain submission. They do
not inject the DLL or send a real message. A maintainer can complete a separate
single self-chat live acceptance before enabling normal recipients.

The original integration additionally exercised one minimized self-chat image
send on 2026-10-21 (new server ID, received image decoded and visually matched,
no foreground change), and one authorized native group mention on 2026-10-22
(new server ID plus matching real-member `atuserlist`, no desktop input).
These are **mapping-level results from the original host**, not end-to-end
acceptance of this portable WeChatAgent revision. Raw receipts, account IDs,
group names, tokens, images and compiled binaries are deliberately not included.
