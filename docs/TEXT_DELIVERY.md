# 回复防重复与回执核验

2026-10-07。现场日志中，同一回复先出现 OneBot 1407，再以 1–4 毫秒重用原决策发送；微信数据库最终有 2–3 条相同文字且服务器 ID 非零，Bridge 缓冲却只有一条 AI 回复。确认是回执漏判后的重复提交。

## 修复

- 微信消息时间可能比本机发送流程早几秒。回执使用当前账号、当前聊天、发送前已有消息 ID、完整文字、新消息 ID 和非零服务器 ID 核验；时间下界改为允许 30 秒偏差。先绑定最早的新匹配记录，即使其服务器 ID 尚未写入，也不借用后续另一条消息的回执。
- 每个回复批次获得稳定的 delivery ID。生成的回复与目标先保存到 Bridge 待发送记录，再提交给发送端。
- 发送端在原生提交前写入操作记录。同一 ID 重试只核对回执或返回已确认结果，不再次调用原生发送；HTTP 响应丢失、WebSocket 重连和进程重启均沿用这一 ID。
- Bridge 重启恢复原决策，不重新生成另一段回复；发出记录、输入处理边界和待发送记录清理在一次缓冲保存中完成。
- 无法确认回执时明确记录 unconfirmed，不冒充已送达，也不持续重发或阻塞后续批次。模型只将这段文字当作未确认的接话参考，不能声称对方已收到。
- 相同的入站事件会在持久化缓冲中去重。不同入站批次拥有不同操作 ID，可以正常回复相同的短句；不使用跨批次的永久文本黑名单。
- 已确认表情也按 delivery ID 保存结果，丢失动作响应后不会重复提交原生表情。

## 数据与边界

Bridge 待发送记录位于 state/social-messages.json 的 pendingReplies；发送操作位于 state/text-deliveries/。这些私有记录包含回复文字和聊天绑定信息，不应发布。状态损坏时拒绝新的提交，不能靠清空记录自动重发。

这是一种避免重复提交的策略，不保证在进程崩溃、断网等所有情形下都送达。提交前已落盘但尚未来得及真正发送时，恢复仍保留未确认状态，不能自动猜测后重新提交。只有查到满足条件的服务器回执才记为确认送达。

## 验证

132 项项目回归通过。覆盖迟到回执、8 秒时钟偏差、原生 HTTP 响应丢失、Bridge 重启后的原决策恢复、已确认结果重用、不同请求合法使用相同文字、未确认批次不重复或阻塞，以及表情确认结果恢复。

真实回执只读审计复用了微信中已经存在的重复记录；审计程序明确禁止原生发送 POST，验证修复能够匹配此前漏掉的记录，未向联系人发送测试消息。私有诊断保存在 state/diagnostics/duplicate-text-diagnosis.json 与 text-receipt-readonly-audit.json。
